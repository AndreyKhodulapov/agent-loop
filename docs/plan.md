# agent-loop: агентный цикл разработки поверх Claude Code CLI — план

Задача: автоматизировать повторяющийся цикл «декомпозиция → задача в свежей сессии → проверка → коммит → ревью → правки» так, чтобы человек участвовал только в проектировании (обсуждение и утверждение плана) и в приёмке итогового диффа перед MR.

Короткий ответ: система реализуема на текущем `claude` CLI (2.1.296) без обходных путей. Всё нужное для управления есть в `-p --output-format stream-json`: usage по каждому запросу, заполнение контекста и проценты лимитов подписки. Остальное — детерминированный оркестратор вокруг CLI, который сам держит состояние, гоняет проверки и коммитит. Модель внутри — сменный исполнитель шага.

Материалы: [desires.md](desires.md) (требования), [theory.md](theory.md) (практики), [example/ralph.sh](example/ralph.sh) (антипример: агент сам выбирает задачу, коммитит и объявляет готовность).

### Желательные, следующие версии

- PROVE: поднять сервис, дёрнуть изменённые ручки, приложить результат к отчёту.
- Red-first тесты (TDD) с защитой тестов от правок исполнителем.
- Критик на другой модели (Codex CLI).
- Метрики: success rate, needs human, attempts, стоимость задачи.
- Параллельные циклы на одной машине (в разных репозиториях).
- Переключение VPN-клиента (Happ) вокруг шагов оркестратора: выключить, поставить зависимости, прогнать, включить с нужным конфигом перед вызовом агента.

### Не делаем

- Мерж, пуш и создание MR. Финальный дифф смотрит человек, MR он же и открывает.
- Ребейз и обновление ветки от базовой.
- Задачи на несколько репозиториев в одном прогоне.
- Prometheus/Grafana. Метрики считаются из SQLite скриптом `loop stats`.
- Внешние workflow-движки (Temporal и пр.): для одного разработчика это лишняя инфраструктура.

## 2. Результаты спайков

### S1. Лимиты и контекст в headless-режиме — сделано 2026-10-10

Запуск `claude -p ... --output-format stream-json --verbose` на 2.1.296.

- В потоке есть событие `rate_limit_event`:
  ```json
  {"type": "rate_limit_event",
   "rate_limit_info": {"status": "allowed", "rateLimitType": "five_hour",
     "unifiedWindows": {"five_hour": {"utilization": 0.01, "resetsAt": 1791670200},
                        "seven_day": {"utilization": 0.64, "resetsAt": 1791813600}}}}
  ```
  `utilization` — доля от 0 до 1 (в statusline это `used_percentage` от 0 до 100), `resetsAt` — unix-секунды. Это те же серверные данные, что видит statusline. Они общие на аккаунт, поэтому расход интерактивных сессий, других циклов и второй машины учитывается автоматически.
- Недельный сброс на этом аккаунте — **понедельник 17:00 по локальному времени**, а не 00:00. Начало недели считаем как `seven_day.resetsAt − 7 суток`, а не по календарю.
- Каждое сообщение `assistant` несёт `message.usage`. Заполнение контекста = `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` последнего сообщения основной цепочки (та же формула, что в statusline).
- `result` содержит `usage`, `modelUsage` (с `contextWindow: 1000000`), `total_cost_usd`, `num_turns`, `permission_denials`, `terminal_reason`.
- Окно у всех моделей 1M, поэтому сама модель на 150k не остановится. Потолок R4 обеспечивает только наш guard.
- В сессии с несколькими вызовами `rate_limit_event` пришёл один раз, после первого ответа. Приходит ли он повторно при изменении процента — неизвестно (см. S1b).
- Даже headless-сессия поднимает встроенные плагины и auto-memory (`memory_paths.auto` есть в `init`). Это нужно отключить настройками цикла (S4).

### S2–S6 — сделано 2026-10-10

Все прогоны на `haiku` в тестовом репозитории, `claude` 2.1.296.

**S2. Hook `PreToolUse` останавливает сессию — подтверждено.**
- Ответ `{"hookSpecificOutput": {"permissionDecision": "deny", "permissionDecisionReason": "..."}}` отклоняет вызов. Причина приходит агенту как результат инструмента (`PreToolUse:Read hook error: <текст>`), и агент её выполняет: в тесте он сразу записал `handoff.md`.
- `{"continue": false}` без `deny` **не отменяет текущий вызов**: инструмент выполняется, сессия завершается сразу после него. Для мягкой остановки это удобно: последний вызов (запись handoff) проходит, дальше стоп.
- `continue: false` вместе с `deny` — жёсткая остановка, инструмент не выполняется.
- В `result`: `terminal_reason: "hook_stopped"`, `subtype: "success"`. Оркестратор отличает такую остановку от обычного завершения.
- Hook получает `session_id`, `transcript_path`, `tool_name`, `tool_input`, `cwd`, `effort`, `permission_mode`. Но транскрипт с `--no-session-persistence` на диск не пишется. Поэтому guard берёт заполнение контекста не из транскрипта, а из файла `live.json`, который оркестратор обновляет из `stream-json`. Сессии цикла всё равно идут с персистентностью (нужна для `--resume`).

**S3. `--json-schema` — подтверждено.**
- Модель отвечает через служебный инструмент `StructuredOutput`. В `result` есть поле `structured_output` (объект) и `result` (та же строка JSON).
- `StructuredOutput` — вызов инструмента, поэтому он тоже проходит через `PreToolUse`. **Guard обязан всегда пропускать `StructuredOutput`**, иначе жёсткая остановка съест финальный ответ шага.
- `maxLength` схемы модель соблюдает, но содержимое строки схема не контролирует. Валидация сообщения коммита остаётся в коде.

**S4. Изоляция настроек — подтверждено, с находками.**
- Без изоляции пользовательские настройки протекают в headless-сессию. В S3 `commit_message` пришёл на русском из-за `"language": "russian"` в `~/.claude/settings.json`.
- С `--setting-sources project --settings loop-settings.json`: `permissionMode` берётся из настроек цикла (`dontAsk`, а не твой `bypassPermissions`), `autoMemoryEnabled: false` отключает память (`memory_paths: null`), ответы на английском. OAuth работает.
- Встроенные плагины (`cc-plugin-agents-md`, `cc-plugin-telemetry`, `cc-plugin-plugin-authoring`) грузятся всегда. Не мешают.
- `"sandbox": {"enabled": true, "autoAllowBashIfSandboxed": true}` работает для Bash: запись в `$HOME` — `operation not permitted`, запись в рабочий каталог проходит. Запись в `$TMPDIR` sandbox тоже разрешает.
- Sandbox ограничивает только Bash. Инструменты `Write`/`Edit` регулируются правилами `permissions`, поэтому разрешаем их только в рабочем каталоге (`Write(./**)`, `Edit(./**)`).

**S5. Запрет без зависания — подтверждено.**
- `dontAsk` + `--permission-prompts none`: всё, чего нет в `allow`, отклоняется мгновенно и попадает в `permission_denials`. Сессия заняла 12 секунд, без ожидания.
- Текст отказа от CLI прямо подсказывает агенту: «You *may* attempt to accomplish this action using other tools». То есть агент будет искать обход. Это ещё один довод за проверку HEAD кодом (раздел 7).

**S6. `--resume` — подтверждено.**
- Возобновление сохраняет `session_id` и контекст. В тесте сразу после паузы 7500 токенов пришли из кэша, создано только 49.
- Кэш живёт час (`ephemeral_1h_input_tokens`). После паузы по бюджету дольше часа первый запрос заново запишет весь контекст в кэш — одноразовая плата до 150k токенов. Это приемлемо.

**S7. Сеть и чтение секретов в sandbox — до этапа 2.2.** Проверить на `loop-settings.json`: (а) Bash в sandbox не выходит наружу (`curl https://pypi.org`), (б) выходит на localhost (тест к Postgres в docker), (в) запрет `Read(.env*)` действует и на `cat .env` из Bash. По S4 проверена только запись.

**S1b** отложен до первого реального прогона: повтор `rate_limit_event` проверим на логах длинной сессии. Пробный вызов, на который можно опереться, если события не повторяются, уже проверен (S1).

## 3. Принятые решения

| 2026-10-10 | Язык оркестратора | Python 3.12+, stdlib (`subprocess`, `sqlite3`, `signal`) + `jsonschema`; запуск через `uv` | Конечный автомат, JSON, сигналы и БД на bash хрупкие; в `ralph.sh` уже есть тихие баги (`grep -c` + `\|\| echo 0` даёт `"0\n0"`) |
| 2026-10-10 | Источник данных о лимитах | `rate_limit_event` из `stream-json` (данные сервера, общие на аккаунт); резерв — пробный вызов | Подтверждено спайком S1; локальный подсчёт токенов не видит другие машины и интерактивные сессии |

## 4. Архитектура

```
loop plan   ──► интерактивная сессия планировщика (claude, с человеком)
                 └► plan.json (по схеме) ──► критик плана (-p, ≤2 итерации) ──► loop approve
loop run    ──► для каждой задачи:
                 budget gate ─► сборка промпта ─► исполнитель (-p, stream-json, guard-hook)
                     ─► gates (fmt, lint, test, инварианты) ─┬─ ок ─► коммит кодом
                                                              └─ fail ─► исполнитель с выводом ошибки (≤N)
                 каждый 2-й коммит ─► ревьюер ─► правки (≤2)
              финальное ревью ветки (≤2) ─► report.md
```

### Компоненты

| Модуль | Ответственность |
|---|---|
| `cli` | Команды `plan`, `approve`, `run`, `resume`, `answer`, `status`, `stats`, `selfcheck` |
| `store` | SQLite: прогоны, задачи, шаги, события, снимки лимитов. Каждый переход — одна транзакция |
| `agent` | Адаптер CLI: собирает аргументы, запускает процесс в отдельной группе, разбирает `stream-json`, отдаёт события (usage, лимиты, результат). Единственное место, знающее флаги `claude`. Позже — адаптер `codex` |
| `guard` | Hook-скрипт `PreToolUse` внутри сессии: читает `live.json` (контекст и лимиты) и stop-файл; просит агента свернуться (`deny` с инструкцией) или останавливает сессию (`continue: false`); `StructuredOutput` пропускает всегда |
| `budget` | Формулы допустимого расхода (раздел 5), решение «можно стартовать шаг», расчёт времени до возобновления |
| `gates` | Детерминированные проверки после шага (раздел 7) |
| `prompts` | Файлы ролей (planner, plan-critic, implementer, fixer, reviewer) и сборка промпта задачи |
| `export` | Рендер `PLAN.md`, `PROGRESS.md`, `report.md` на выбранном языке в каталог истории |
| `log` | Терминальный лог: `[run 3f2a] [task 2/7] [implement] ctx 84k/150k · 5h 31%/48% · 7d 52%/57%` |

### Состояния задачи

```
pending → implementing → gating → committed → (reviewing → fixing)* → done
             │  ↑            │
             │  └── fixing ◄─┘ (тесты/линтер упали, попытка ≤ N)
             ├─► paused (бюджет | контекст | Ctrl+C | таймаут) ──► implementing
             ├─► needs_human ──► (loop answer) ──► implementing
             └─► replan (дифф > потолка | 2 паузы по контексту на задаче | исчерпаны попытки)
                   └─► пересмотр всех оставшихся задач (keep / modify / drop) ─► критик (1 итерация) ─► pending
```

Каждый шаг идемпотентен: перед запуском в БД пишется `started`, после — `finished` с результатом. При рестарте незавершённый шаг либо откатывается к чекпоинту, либо возобновляется. Так же решается двойное создание артефактов.

## 5. Бюджет лимитов (R7, R8)

Пусть `u5`, `u7` — текущие `utilization`, `now` — текущее время.

Недельный потолок:
```
week_start = seven_day.resetsAt − 7d
k          = floor((now − week_start) / 24h) + 1        # день недели от сброса, 1..7
cap7       = k / 7 − reserve7
```
Сброс в понедельник 17:00, значит, до среды 16:59 включительно (`k = 2`) потолок 2/7, а в течение третьих суток — 3/7.

5-часовое окно:
```
window_start = five_hour.resetsAt − 5h
e            = now − window_start
cap5         = min(1, s + (1 − s) · e / 4h) − reserve5
```
`s` — стартовый запас (по умолчанию 0.2), иначе первые минуты окна почти без бюджета. При `e = 4h` потолок становится 1: стопроцентный расход возможен только в последний час окна. Если активного окна нет (`five_hour` не пришёл), шаг разрешён.

`reserve5`, `reserve7` — резерв на ручную работу, которая идёт параллельно (по умолчанию 0.10 и 0.05).

Правила:
- **Перед шагом:** старт разрешён, если `u5 < cap5 − margin` и `u7 < cap7 − margin`, где `margin` — оценка расхода шага (из истории, по умолчанию 3%). Иначе прогон в `paused(budget)` до момента, когда кривая догонит `u + margin` (время считается из формулы) или до сброса окна. В логе: время возобновления.
- **Внутри шага:** оркестратор пишет свежие лимиты в `~/.agent-loop/limits.json` (атомарная запись). Guard на каждом вызове инструмента сравнивает с потолком: при превышении просит агента свернуться (раздел 6), при превышении ещё на 2% останавливает сессию.
- **Несколько циклов:** все пишут и читают один `limits.json`; данные серверные, поэтому суммирование выходит само собой.

## 6. Потолок контекста и контролируемая остановка (R4, R8, R9)

Один механизм на все причины остановки: `budget`, `context`, `interrupt`, `timeout`.

1. Причина фиксируется в stop-файле прогона (`~/.agent-loop/runs/<run>/stop`) или вычисляется guard'ом (контекст, лимиты).
2. **Мягкая граница** (контекст ≥ 120k, лимит достиг потолка, первый Ctrl+C, таймаут шага): guard на ближайшем вызове инструмента отклоняет его с инструкцией: «Остановись. Запиши в `.loop/handoff.md`: что сделано, что осталось, какие файлы в работе. Заверши ход».
3. **Жёсткая граница** (контекст ≥ 150k или агент не свернулся за 3 вызова): guard возвращает `continue: false`, сессия завершается.
4. Оркестратор сохраняет незакоммиченную работу в ref `refs/loop/wip/<run>/<task>` (`git stash create` + `update-ref`), пишет в БД `paused` с причиной и session_id, экспортирует прогресс.
5. Второй Ctrl+C: SIGTERM процессу `claude`, затем шаг 4 и выход. Для этого `claude` запускается в отдельной группе процессов, иначе SIGINT от терминала убьёт его раньше обработчика.

Возобновление:
- после паузы по бюджету, Ctrl+C или таймауту — `--resume <session_id>` (контекст < 150k; S6: после паузы дольше часа кэш создаётся заново);
- после паузы по контексту — новая сессия: карточка задачи + `handoff.md` + `git diff` WIP. Вторая пауза по контексту на той же задаче отправляет её в `replan`: задача слишком большая.

Ограничение: guard срабатывает только между вызовами инструментов. Длинная команда (например, тесты) доработает до конца, поэтому граница 120k оставляет запас.

## 7. Gates: инварианты проверяет код

После каждого шага исполнителя, до коммита:

| Проверка | Как | При нарушении |
|---|---|---|
| Агент не коммитил | `git rev-parse HEAD` до и после шага; запрет `git commit/push/reset/checkout` в настройках — только первая линия обороны | Откат к чекпоинту, шаг заново, инцидент в лог |
| Тесты не ослаблены | Число собранных тестов (`pytest --collect-only -q`) не уменьшилось; в диффе нет новых `skip`/`xfail`/удалённых `assert`; после red-фазы (v2) хеши тестовых файлов неизменны | Возврат исполнителю с конкретной находкой; повтор — `needs_human` |
| Ветка не тронута человеком | Перед шагом и перед коммитом: текущая ветка и HEAD совпадают с записанными в БД | `paused(branch_changed)`, сообщение оператору |
| Зависимости | Изменились файлы из `deps_files` профиля — оркестратор запускает `install` до остальных проверок | Упал `install` — fixer с выводом |
| fmt / lint / test | Команды из профиля репозитория, с таймаутами. Упавшие тесты перезапускаются один раз; прошли со второго раза — флакающий тест (раздел 3) | Исполнитель-fixer получает хвост вывода (последние ~200 строк), не больше N=3 попыток |
| Секреты в коммите | Новые неотслеживаемые файлы сверяются с шаблонами `.env*`, `*.pem`, `*.key`, `*credentials*` и `secret_patterns` профиля | Файл не коммитится, находка в отчёт; если без него не собирается — `needs_human` |
| Размер диффа | `git diff --numstat` против чекпоинта | > 1000 — предупреждение в отчёт; > 1500 — `replan` |
| Сообщение коммита | Схема ответа: `type(scope): gist`, ≤ 72 символов, английский; регулярка запрещает `Co-Authored-By`, `Claude`, `Anthropic`, `Generated with` | Повторный запрос сообщения (1 раз), затем шаблон из заголовка задачи |
| Стиль (детерминированная часть шаблона ревью) | Регулярки: декоративные разделители `# ---`, markdown в докстрингах, ссылки на номера задач/решений из плана; AST: глобальная переменная, использованная в модуле меньше 3 раз | Возврат исполнителю |
| Субагенты | `--disallowedTools Agent` для исполнителя и fixer | — |

Коммит делает оркестратор, автор — пользователь из git config. Не `git add -A`: в индекс попадают изменённые отслеживаемые файлы и неотслеживаемые, появившиеся за шаг (список неотслеживаемых снимается перед шагом), кроме файлов из проверки секретов.

Откат к чекпоинту тоже точечный: `git reset --hard <checkpoint>` и удаление только тех неотслеживаемых файлов, что появились за шаг. `git clean` по всему каталогу не делаем: там лежат `.env`, сертификаты и прочее окружение.

## 8. Контекст исполнителя (R3)

Промпт задачи собирает оркестратор, агент не читает план и прогресс сам:

- роль (файл `prompts/implementer.md`);
- карточка задачи из `plan.json`: цель, критерии приёмки, файлы-подсказки, тесты, которые должны пройти, бюджет диффа;
- решения из плана, помеченные для этой задачи;
- сводка предыдущих задач, собранная кодом: список изменённых файлов и новых публичных символов (`git diff --name-status` + разбор AST). Без неё агент задачи N пишет свою утилиту вместо созданной в задаче N−1;
- правила: `AGENTS.md` agent-loop и `context_file` проекта — через `--append-system-prompt-file`; CLAUDE.md, лежащий в репозитории, подтягивается штатно (selfcheck проверяет, что так и есть при `--setting-sources project`);
- язык комментариев и докстрингов из конфига;
- при возобновлении — `handoff.md`.

Ответ исполнителя по схеме: `status` (`done` / `blocked` / `needs_human`), `summary`, `commit_message`, `notes_for_next`, `question`.

Агенту разрешено запускать только тесты, относящиеся к задаче (быстрые). Полный прогон делает gate.

## 10. Безопасность и настройки сессий

Сейчас: `~/.claude/settings.json` — `defaultMode: bypassPermissions` плюс deny-список (`rm -rf *`, `export *KEY*`, `curl *TOKEN*` и т. п.). Deny-список по шаблонам обходится тривиально: `find -delete`, `python -c "shutil.rmtree(...)"`, `cat .env`, `printenv`. Это защита от случайности, а не от агента, который «решил» что-то сделать.

Для цикла:
- Отдельный `loop-settings.json` (`--setting-sources project --settings loop-settings.json`, пользовательские настройки не подтягиваются — проверено в S4): allow-список команд (`uv`, `pytest`, `ruff`, `flake8`, `make <цели профиля>`, `git status/diff/log/show`), deny на `git commit/push/reset/checkout/rebase`, `rm -rf`, сетевые утилиты; `sandbox` для Bash (запись только в рабочий каталог и `$TMPDIR`), сеть из sandbox закрыта; `Write`/`Edit` разрешены только в рабочем каталоге, `Read`/`Write`/`Edit` запрещены для `.env*`, `*.pem`, `*.key`; `autoMemoryEnabled: false`.
- Чистое окружение: `claude` запускается с `env`, где оставлены только `PATH`, `HOME`, `LANG` и переменные из профиля репозитория. Токены и ключи из shell не наследуются.
- Инварианты из раздела 7 ловят то, что пропустили настройки.

### Работа в текущей ветке: риски и защиты

| Риск | Защита |
|---|---|
| Незакоммиченные правки человека смешаются с работой агента, попадут в его коммит или пропадут при откате | `loop run` не стартует, если есть изменения в отслеживаемых файлах. Неотслеживаемые файлы на старте запоминаются и не трогаются |
| Человек переключил ветку, сделал коммит или ребейз во время прогона — агент продолжит писать в чужое состояние | Проверка ветки и HEAD перед каждым шагом и перед коммитом (раздел 7) → пауза |
| Агенту видны `.env` и сертификаты (в worktree их бы не было) | Запрет `Read`/`Edit` на эти пути; токены не наследуются из shell. Закрывает ли запрет `Read` чтение через Bash в sandbox (`cat .env`) — спайк S7. Если нет, принимаем риск: у инструментов агента нет выхода в сеть. Но прочитанное попадает в контекст и уходит в API Anthropic, как в любой сессии |
| `git add -A` закоммитит мусор или секреты | Точечное добавление файлов (раздел 7) |
| Откат к чекпоинту снесёт окружение | Точечный откат, без `git clean` (раздел 7) |
| Два прогона в одном каталоге | Lock-файл `.git/agent-loop.lock` с pid; второй `loop run` отказывается стартовать |
| Служебные файлы цикла (`.loop/handoff.md`) попадут в коммит | `.loop/` добавляется в `.git/info/exclude` при старте |
| Сервис, запущенный человеком с `--reload`, перезапускается на каждой правке агента | Безвредно; если мешает — останавливать сервис на время прогона |

Пока прогон идёт, рабочий каталог принадлежит циклу: читать и запускать сервис можно, править файлы и двигать ветку — нет.

Отдельная задача вне цикла: собрать `COLLECTION/claude_settings/` (settings.json + установка) по образцу `claude_statusline`, чтобы глобальные настройки на обеих машинах совпадали.

## 11. Таймауты

| Уровень | Значение по умолчанию | Что ловит |
|---|---|---|
| Команда Bash внутри сессии | `BASH_DEFAULT_TIMEOUT_MS` / `BASH_MAX_TIMEOUT_MS` в окружении цикла (2 / 10 мин) | Зависший тест, запущенный агентом |
| Простой потока | Нет событий `stream-json` дольше максимального таймаута Bash + 2 мин | Зависание самого CLI или сети |
| Шаг целиком | 60 мин | Агент ходит по кругу; мягкая остановка через stop-файл, через 5 мин — жёсткая |
| Gate-команды | Из профиля репозитория | Зависший полный прогон; рекомендуется `pytest-timeout` |

Тесты из цикла не исключаем: агент гоняет только быстрые тесты своей задачи, полный прогон делает gate с собственным таймаутом.

## 12. Все роли на Opus: риски

Главную пользу независимого ревью даёт свежий контекст: критик не видел рассуждений исполнителя и не «помнит», почему решение казалось верным. Это мы получаем и на одной модели. Чего не получаем:

- **Коррелированные слепые зоны.** Одинаково ошибочное представление о поведении библиотеки или API у исполнителя и критика — критик подтвердит ошибку.
- **Предпочтение своего стиля.** Модель мягче оценивает код, написанный в её собственной манере, в том числе признаки AI-кода из шаблона ревью.
- **Принятие рамки плана.** Критик читает план, написанный той же моделью, и склонен спорить с деталями, а не с постановкой.

Что делаем:
- критику — только дифф, карточку задачи и доступ к репозиторию на чтение; без логов исполнителя;
- роль критика — состязательная; каждая блокирующая находка обязана содержать файл:строку и сценарий отказа, без них не блокирует;
- критику — `--effort max`, исполнителю — `high`;
- всё, что можно проверить кодом, уходит из ревью в gates (раздел 7): критику остаётся логика;
- метрика: доля находок критика, которые после правки действительно что-то изменили. Когда появится адаптер Codex, прогоняем обоих критиков на одних и тех же диффах и считаем расхождения. Это ответ на вопрос «насколько хуже» на наших данных, а не на ощущениях.

## 14. Этапы

Каждый этап — серия коммитов ≤ ~1000 строк. Номера коммитов внутри этапа уточняются при старте этапа.

### Этап 0. Спайки — сделано 2026-10-10
S1–S6 в разделе 2. S1b проверяется на первом реальном прогоне.

### Этап 1. Каркас
1. `uv`-проект, `AGENTS.md`, `.env.example`, CLI `loop` с подкомандами-заглушками, конфиг (`.env` → `loop.toml` → флаги: язык, модели, пути, пороги), терминальный лог.
2. `store`: схема SQLite, миграция, транзакционные переходы состояний.
3. `agent`: запуск `claude -p` в отдельной группе процессов, разбор `stream-json` в типизированные события, запись сырого потока в `runs/<run>/`; `loop selfcheck`.

### Этап 2. Guard и бюджет
1. `budget`: формулы раздела 5, расчёт времени возобновления, `limits.json`; тесты на граничные моменты (сброс, понедельник 17:00, нет окна).
2. `guard`: hook-скрипт (контекст и лимиты из `live.json`, stop-файл), `loop-settings.json`.
3. Ctrl+C и таймауты: двухступенчатая остановка, WIP-ref, возобновление через `--resume` и через handoff; финализатор и доуборка мёртвых прогонов при старте, `loop gc`.

### Этап 3. Цикл реализации
1. Профиль репозитория, `gates`: `install` по изменению зависимостей, команды, перезапуск упавших тестов, инварианты ветки/HEAD, тестов, диффа, секретов; lock рабочего каталога.
2. Сборка промпта задачи, роль исполнителя, схема ответа, цикл fixer (≤3).
3. Коммит кодом с валидацией сообщения; детерминированные проверки стиля.

### Этап 4. Планирование
1. Схема `plan.json`, роль планировщика, интерактивный режим (`loop plan`) и headless-режим (`loop plan --from task.md` с `QUESTIONS.md` и `loop answer`), валидация на выходе.
2. Критик плана (≤2 итерации), `loop approve` (фиксирует хеш плана), рендер `PLAN.md`; перепланирование посреди прогона (keep / modify / drop).

### Этап 5. Ревью
1. Ревью каждого 2-го коммита и финальное ревью ветки; схема вердикта (severity, файл:строка, сценарий); цикл правок ≤2; деление диффа, если он не влезает в 150k.
2. `report.md`.

### Этап 6. История и метрики
Экспорт в `agent_runs/`, `loop stats`, уведомления для `needs_human` (macOS notification + `say`, опционально `COLLECTION/tg_notifier`).
