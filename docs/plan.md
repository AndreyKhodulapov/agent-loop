# agent-loop: агентный цикл разработки поверх Claude Code CLI — план

Задача: автоматизировать повторяющийся цикл «декомпозиция → задача в свежей сессии → проверка → коммит → ревью → правки» так, чтобы человек участвовал только в проектировании (обсуждение и утверждение плана) и в приёмке итогового диффа перед MR.

Короткий ответ: система реализуема на текущем `claude` CLI (2.1.296) без обходных путей. Всё нужное для управления есть в `-p --output-format stream-json`: usage по каждому запросу, заполнение контекста и проценты лимитов подписки. Остальное — детерминированный оркестратор вокруг CLI, который сам держит состояние, гоняет проверки и коммитит. Модель внутри — сменный исполнитель шага.

Материалы: [desires.md](desires.md) (требования), [theory.md](theory.md) (практики), [example/ralph.sh](example/ralph.sh) (антипример: агент сам выбирает задачу, коммитит и объявляет готовность).

### Желательные, следующие версии

- PROVE: поднять сервис, дёрнуть изменённые ручки, приложить результат к отчёту.
- Red-first тесты (TDD) с защитой тестов от правок исполнителем.
- Критик на другой модели (Codex CLI).
- Метрики: success rate, needs human, attempts, стоимость задачи.
- Параллельные циклы на одной машине (в разных репозиториях).
- Переключение VPN-клиента (Happ) вокруг шагов оркестратора: выключить, поставить зависимости, прогнать, включить с нужным конфигом перед вызовом агента.

### Не делаем

- Мерж, пуш и создание MR. Финальный дифф смотрит человек, MR он же и открывает.
- Ребейз и обновление ветки от базовой.
- Задачи на несколько репозиториев в одном прогоне.
- Prometheus/Grafana. Метрики считаются из SQLite скриптом `loop stats`.
- Внешние workflow-движки (Temporal и пр.): для одного разработчика это лишняя инфраструктура.

## 2. Результаты спайков

### S1. Лимиты и контекст в headless-режиме — сделано 2026-10-10

Запуск `claude -p ... --output-format stream-json --verbose` на 2.1.296.

- В потоке есть событие `rate_limit_event`:
  ```json
  {"type": "rate_limit_event",
   "rate_limit_info": {"status": "allowed", "rateLimitType": "five_hour",
     "unifiedWindows": {"five_hour": {"utilization": 0.01, "resetsAt": 1791670200},
                        "seven_day": {"utilization": 0.64, "resetsAt": 1791813600}}}}
  ```
  `utilization` — доля от 0 до 1 (в statusline это `used_percentage` от 0 до 100), `resetsAt` — unix-секунды. Это те же серверные данные, что видит statusline. Они общие на аккаунт, поэтому расход интерактивных сессий, других циклов и второй машины учитывается автоматически.
- Недельный сброс на этом аккаунте — **понедельник 17:00 по локальному времени**, а не 00:00. Начало недели считаем как `seven_day.resetsAt − 7 суток`, а не по календарю.
- Каждое сообщение `assistant` несёт `message.usage`. Заполнение контекста = `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` последнего сообщения основной цепочки (та же формула, что в statusline).
- `result` содержит `usage`, `modelUsage` (с `contextWindow: 1000000`), `total_cost_usd`, `num_turns`, `permission_denials`, `terminal_reason`.
  На `--resume` `total_cost_usd` и `modelUsage` накопительные за всю сессию, а `usage` и `num_turns` — за вызов (прогон `584816d9`, 2026-10-16).
- Окно у всех моделей 1M, поэтому сама модель на 150k не остановится. Потолок R4 обеспечивает только наш guard.
- В сессии с несколькими вызовами `rate_limit_event` пришёл один раз, после первого ответа. Приходит ли он повторно при изменении процента — неизвестно (см. S1b).
- Даже headless-сессия поднимает встроенные плагины и auto-memory (`memory_paths.auto` есть в `init`). Это нужно отключить настройками цикла (S4).

### S2–S6 — сделано 2026-10-10

Все прогоны на `haiku` в тестовом репозитории, `claude` 2.1.296.

**S2. Hook `PreToolUse` останавливает сессию — подтверждено.**
- Ответ `{"hookSpecificOutput": {"permissionDecision": "deny", "permissionDecisionReason": "..."}}` отклоняет вызов. Причина приходит агенту как результат инструмента (`PreToolUse:Read hook error: <текст>`), и агент её выполняет: в тесте он сразу записал `handoff.md`.
- `{"continue": false}` без `deny` **не отменяет текущий вызов**: инструмент выполняется, сессия завершается сразу после него. Для мягкой остановки это удобно: последний вызов (запись handoff) проходит, дальше стоп.
- `continue: false` вместе с `deny` — жёсткая остановка, инструмент не выполняется.
- В `result`: `terminal_reason: "hook_stopped"`, `subtype: "success"`. Оркестратор отличает такую остановку от обычного завершения.
- Hook получает `session_id`, `transcript_path`, `tool_name`, `tool_input`, `cwd`, `effort`, `permission_mode`. Но транскрипт с `--no-session-persistence` на диск не пишется. Поэтому guard берёт заполнение контекста не из транскрипта, а из файла `live.json`, который оркестратор обновляет из `stream-json`. Сессии цикла всё равно идут с персистентностью (нужна для `--resume`).

**S3. `--json-schema` — подтверждено.**
- Модель отвечает через служебный инструмент `StructuredOutput`. В `result` есть поле `structured_output` (объект) и `result` (та же строка JSON).
- `StructuredOutput` — вызов инструмента, поэтому он тоже проходит через `PreToolUse`. **Guard обязан всегда пропускать `StructuredOutput`**, иначе жёсткая остановка съест финальный ответ шага.
- `maxLength` схемы модель соблюдает, но содержимое строки схема не контролирует. Валидация сообщения коммита остаётся в коде.

**S4. Изоляция настроек — подтверждено, с находками.**
- Без изоляции пользовательские настройки протекают в headless-сессию. В S3 `commit_message` пришёл на русском из-за `"language": "russian"` в `~/.claude/settings.json`.
- С `--setting-sources project --settings loop-settings.json`: `permissionMode` берётся из настроек цикла (`dontAsk`, а не твой `bypassPermissions`), `autoMemoryEnabled: false` отключает память (`memory_paths: null`), ответы на английском. OAuth работает.
- Встроенные плагины (`cc-plugin-agents-md`, `cc-plugin-telemetry`, `cc-plugin-plugin-authoring`) грузятся всегда. Не мешают.
- `"sandbox": {"enabled": true, "autoAllowBashIfSandboxed": true}` работает для Bash: запись в `$HOME` — `operation not permitted`, запись в рабочий каталог проходит. Запись в `$TMPDIR` sandbox тоже разрешает.
- Sandbox ограничивает только Bash. Инструменты `Write`/`Edit` регулируются правилами `permissions`, поэтому разрешаем их только в рабочем каталоге (`Write(./**)`, `Edit(./**)`).

**S5. Запрет без зависания — подтверждено.**
- `dontAsk` + `--permission-prompts none`: всё, чего нет в `allow`, отклоняется мгновенно и попадает в `permission_denials`. Сессия заняла 12 секунд, без ожидания.
- Текст отказа от CLI прямо подсказывает агенту: «You *may* attempt to accomplish this action using other tools». То есть агент будет искать обход. Это ещё один довод за проверку HEAD кодом (раздел 7).

**S6. `--resume` — подтверждено.**
- Возобновление сохраняет `session_id` и контекст. В тесте сразу после паузы 7500 токенов пришли из кэша, создано только 49.
- Кэш живёт час (`ephemeral_1h_input_tokens`). После паузы по бюджету дольше часа первый запрос заново запишет весь контекст в кэш — одноразовая плата до 150k токенов. Это приемлемо.

**S7. Сеть и чтение секретов в sandbox — сделано 2026-10-11** (`haiku`, 2.1.296, настройки `src/agent_loop/loop-settings.json`):
- Наружу Bash не выходит: `curl` отклонён правилом `deny`, а запрос из Python к pypi.org режет прокси sandbox (`403` на CONNECT, `deny network-outbound`). Список `network.allowedDomains` пуст, в `dontAsk` новый домен не спрашивается, а отклоняется.
- localhost доступен при `sandbox.network.allowLocalBinding: true` (на macOS; на Linux этот ключ не действует, там клиент БД пришлось бы выносить в `excludedCommands`).
- `cat .env` и `head cert.pem` из Bash — `Operation not permitted`: запреты `Read(.env*)`, `Read(*.pem)` попадают и в файловые ограничения sandbox. Содержимое секретов в поток не попало.
- `sandbox.allowUnsandboxedCommands: false` обязателен: по умолчанию агент может повторить команду вне sandbox (`dangerouslyDisableSandbox`). `failIfUnavailable: true` — без sandbox сессия не стартует.
- Правило `Edit(./**)` покрывает и `Write`; запись вне рабочего каталога отклонена. `Bash(git commit *)` отклонён, коммита нет.
- Hook работает вне sandbox (может писать в `~/.agent-loop/runs/<run>/`). В окружении Bash секретов нет, но есть служебные `CLAUDE_CODE_*`.
- Guard на реальном CLI: при stop-файле агент получил отказ, записал `.loop/handoff.md` и ответил по схеме (`terminal_reason: completed`); при контексте выше жёсткой границы — `terminal_reason: hook_stopped`.

**Находки шага 1.3 (2.1.296):**
- `--append-system-prompt-file` в `--help` не показан, но работает. Из нескольких таких флагов действует только последний, поэтому адаптер склеивает файлы правил в один.
- `--session-id <uuid>` задаёт id новой сессии: оркестратор знает его до старта процесса и пишет в БД заранее, `kill -9` не теряет id для `--resume`.

- Ошибка API (неизвестная модель) приходит как `result` с `subtype: "success"`, `is_error: true`, `terminal_reason: "api_error"`; неизвестный флаг — код 1 и текст в stderr без единого события.

Роль из файла действует, режим `dontAsk` («don't ask on» в строке состояния), guard из `--settings` вызывается на каждый вызов и отклоняет его по stop-файлу (`guard.json`: `interrupt`, `denied: 1`). Транскрипт — `~/.claude/projects/<cwd, / заменены на ->/<session-id>.jsonl`, id из `--session-id`.
- Транскрипт не пишется, если в окружении унаследован `CLAUDE_CODE_CHILD_SESSION` («Transcript saving is off»): так будет, если `loop` запущен из сессии Claude Code. Фильтр `agent.ENV_KEYS` эту переменную отрезает; интерактивному запуску в списке нужен ещё `TERM`.
- В каталоге, которому CLI ещё не доверяет, интерактивный режим сначала спрашивает «Do you trust this folder» (по умолчанию «No, exit»), `--restricted` этого не снимает. Ответ запоминается в `~/.claude.json`, в `-p` вопроса нет. Отвечает человек.
- Главный вопрос: после выхода `claude -p --resume <тот же id> --json-schema <схема> --output-format stream-json` продолжает разговор (тот же `session_id`, модель помнит роль и сказанное в интерактивной части) и отдаёт `structured_output`, `terminal_reason: completed`. `--settings` продолжения может отличаться от интерактивного. Запасной путь с `.loop/plan.json` не нужен.
- Расход интерактивной части в поток цикла не попадает: потока у неё нет. Входит ли он в `total_cost_usd` продолжения, не проверялось; загрузка 5h/7d общая на аккаунт и придёт с `rate_limit_event` продолжения.
- Bash без записи: `Edit(./**)` в `deny` (и без `Edit` в `allow`). CLI сливает пути правил `Edit(...)` из `deny` с `sandbox.filesystem.denyWrite`, и запись Bash во весь рабочий каталог закрыта (`touch`, `mkdir` — `Operation not permitted`). Тот же результат дают `sandbox.filesystem.denyWrite` с абсолютным путём репозитория или `"."`. `$TMPDIR` Bash (`/tmp/claude-<uid>`) и `tempfile` по-прежнему открыты на запись, `/tmp` — нет, `git status` работает. Берём `Edit(./**)` в `deny`: без нового ключа настроек.
- Ctrl+C: интерактивный CLI держит терминал в raw-режиме, поэтому Ctrl+C — ввод для CLI, а не SIGINT группе процессов: родитель на Python в той же группе сигнала не получил. Первое Ctrl+C прерывает ход (команда агента убита, «Interrupted · What should Claude do instead?»), двойное подряд — выход с кодом 0 и строкой `claude --resume <id>`; два нажатия с паузой около секунды выходом не считаются. Код выхода не отличает конец разговора от Ctrl+C. Прерванная сессия продолжается через `-p --resume` со схемой; прерванный вызов модель видит как отклонённый пользователем.
- Мягкая остановка guard велит записать `.loop/handoff.md`, а планировщик писать не может: агент ответил текстом и предложил человеку записать handoff самому. Планировщику нужна своя инструкция остановки — закончить ход; продолжение — тот же разговор через `--resume`.

## 4. Архитектура

```
loop plan   ──► интерактивная сессия планировщика (claude, с человеком)
                 └► plan.json (по схеме) ──► критик плана (-p, ≤2 итерации) ──► loop approve
loop run    ──► для каждой задачи:
                 budget gate ─► сборка промпта ─► исполнитель (-p, stream-json, guard-hook)
                     ─► gates (fmt, lint, test, инварианты) ─┬─ ок ─► коммит кодом
                                                              └─ fail ─► исполнитель с выводом ошибки (≤N)
                 каждый 2-й коммит ─► ревьюер ─► правки (≤2)
              финальное ревью ветки (≤2) ─► report.md
```

### Компоненты

| Модуль | Ответственность |
|---|---|
| `cli` | Команды `plan`, `approve`, `run`, `resume`, `answer`, `status`, `stats`, `selfcheck`, `gc`, `config` (действующие настройки и источник каждой) |
| `store` | SQLite: прогоны, задачи, шаги, события, снимки лимитов. Каждый переход — одна транзакция |
| `agent` | Адаптер CLI: собирает аргументы, запускает процесс в отдельной группе, разбирает `stream-json`, отдаёт события (usage, лимиты, результат). Единственное место, знающее флаги `claude`. Позже — адаптер `codex` |
| `guard` | Hook-скрипт `PreToolUse` внутри сессии: читает `live.json` (контекст и лимиты) и stop-файл; просит агента свернуться (`deny` с инструкцией) или останавливает сессию (`continue: false`); `StructuredOutput` пропускает всегда |
| `budget` | Формулы допустимого расхода (раздел 5), решение «можно стартовать шаг», расчёт времени до возобновления |
| `gates` | Детерминированные проверки после шага (раздел 7) |
| `prompts` | Файлы ролей (planner, plan-critic, implementer, fixer, reviewer) и сборка промпта задачи |
| `export` | Рендер `PLAN.md`, `PROGRESS.md`, `report.md` на выбранном языке в каталог истории |
| `log` | Терминальный лог: `[run 3f2a] [task 2/7] [implement] ctx 84k/150k · 5h 31%/48% · 7d 52%/57%` |

### Состояния задачи

```
pending → implementing → gating → committed → (reviewing → fixing → gating → committed)* → done
             │            ↑  │
             │            └─ fixing (тесты/линтер упали, попытка ≤ N; правка снова проходит gates)
             ├─► paused (бюджет | контекст | Ctrl+C | таймаут) ──► стадия прерванного шага
             ├─► needs_human ──► (loop answer) ──► implementing | fixing
             └─► replan (дифф > потолка | 2 паузы по контексту на задаче | исчерпаны попытки)
                   └─► пересмотр всех оставшихся задач (keep / modify / drop) ─► критик (1 итерация) ─► pending
```

Каждый шаг идемпотентен: перед запуском в БД пишется `started`, после — `finished` с результатом. При рестарте незавершённый шаг либо откатывается к чекпоинту, либо возобновляется. Так же решается двойное создание артефактов.

## 5. Бюджет лимитов (R7, R8)

Пусть `u5`, `u7` — текущие `utilization`, `now` — текущее время.

Недельный потолок:
```
week_start = seven_day.resetsAt − 7d
k          = floor((now − week_start) / 24h) + 1        # день недели от сброса, 1..7
cap7       = k / 7 − reserve7
```
Сброс в понедельник 17:00, значит, до среды 16:59 включительно (`k = 2`) потолок 2/7, а в течение третьих суток — 3/7.

5-часовое окно:
```
window_start = five_hour.resetsAt − 5h
e            = now − window_start
cap5         = min(1, s + (1 − s) · e / 4h) − reserve5
```
`s` — стартовый запас (по умолчанию 0.2), иначе первые минуты окна почти без бюджета. При `e = 4h` потолок становится 1: стопроцентный расход возможен только в последний час окна. Если активного окна нет (`five_hour` не пришёл или его `resetsAt` уже прошёл — сервер открыл новое окно), шаг разрешён.

`reserve5`, `reserve7` — резерв на ручную работу, которая идёт параллельно (по умолчанию 0.10 и 0.05).

Правила:
- **Перед шагом:** старт разрешён, если `u5 < cap5 − margin` и `u7 < cap7 − margin`, где `margin` — оценка расхода шага (из истории, по умолчанию 3%). Иначе прогон в `paused(budget)` до момента, когда кривая догонит `u + margin` (время считается из формулы) или до сброса окна. В логе: время возобновления.
- **Внутри шага:** оркестратор пишет свежие лимиты в `~/.agent-loop/limits.json` (атомарная запись; окно, которого нет в событии, сохраняет прежнее значение). Guard на каждом вызове инструмента сравнивает с потолком: при превышении просит агента свернуться (раздел 6), при превышении ещё на 2% останавливает сессию.
- **Несколько циклов:** все пишут и читают один `limits.json`; данные серверные, поэтому суммирование выходит само собой.

## 6. Потолок контекста и контролируемая остановка (R4, R8, R9)

Один механизм на все причины остановки: `budget`, `context`, `interrupt`, `timeout`.

1. Причина фиксируется в stop-файле прогона (`~/.agent-loop/runs/<run>/stop`) или вычисляется guard'ом (контекст, лимиты).
2. **Мягкая граница** (контекст ≥ 120k, лимит достиг потолка, первый Ctrl+C, таймаут шага): guard на ближайшем вызове инструмента отклоняет его с инструкцией: «Остановись. Запиши в `.loop/handoff.md`: что сделано, что осталось, какие файлы в работе. Заверши ход».
3. **Жёсткая граница** (контекст ≥ 150k или агент не свернулся за 3 вызова): guard возвращает `continue: false`, сессия завершается.
4. Оркестратор сохраняет незакоммиченную работу в ref `refs/loop/wip/<run>/<task>` (коммит поверх HEAD через временный индекс: изменения отслеживаемых файлов и неотслеживаемые файлы, появившиеся за шаг; `git stash create` новые файлы не берёт), пишет в БД `paused` с причиной и session_id, экспортирует прогресс.
5. Второй Ctrl+C: SIGTERM процессу `claude`, затем шаг 4 и выход. Для этого `claude` запускается в отдельной группе процессов, иначе SIGINT от терминала убьёт его раньше обработчика.

Возобновление:
- после паузы по бюджету, Ctrl+C или таймауту — `--resume <session_id>` (контекст < 150k; S6: после паузы дольше часа кэш создаётся заново);
- после паузы по контексту — новая сессия: карточка задачи + `handoff.md` + `git diff` WIP. Вторая пауза по контексту на той же задаче отправляет её в `replan`: задача слишком большая.

Ограничение: guard срабатывает только между вызовами инструментов. Длинная команда (например, тесты) доработает до конца, поэтому граница 120k оставляет запас.

## 7. Gates: инварианты проверяет код

После каждого шага исполнителя, до коммита:

| Проверка | Как | При нарушении |
|---|---|---|
| Агент не коммитил | HEAD и ветка совпадают с чекпоинтом шага (`gates.branch_moved`); запрет `git commit/push/reset/checkout` в настройках — только первая линия обороны | `paused(branch_changed)`, как для человека: коммит агента от коммита человека не отличить (раздел 3) |
| Тесты не ослаблены | Число собранных тестов (команда `collect` профиля) не уменьшилось; в диффе тестовых файлов в сумме не прибавилось `skip`/`xfail` и не убавилось строк с `assert` (по всем тестовым файлам вместе: перенос теста не находка); после red-фазы (v2) хеши тестовых файлов неизменны | Возврат исполнителю с конкретной находкой; повтор — `needs_human` |
| Ветка не тронута человеком | Перед шагом и перед коммитом: текущая ветка и HEAD совпадают с записанными в БД | `paused(branch_changed)`, сообщение оператору |
| Зависимости | Изменились файлы из `deps_files` профиля — оркестратор запускает `install` до остальных проверок | Упал `install` — fixer с выводом |
| fmt / lint / test | Команды из профиля репозитория, с таймаутами, под `sandbox-exec` (раздел 10, шаг 3.3в). Упавшие тесты перезапускаются один раз (повтор `test`); прошли со второго раза — флакающий тест (раздел 3) | Исполнитель-fixer получает хвост вывода (последние ~200 строк), не больше N=3 попыток |
| Секреты в коммите | Новые файлы работы сверяются с шаблонами `.env*`, `*.pem`, `*.key`, `*credentials`, `*credentials*.json`, `*credentials*.yaml`, `*credentials*.yml` и `secret_patterns` профиля — до команд профиля (решение 2026-10-12, ревью 3а.1: `*credentials*` ловил `test_credentials.py`) | Файл не коммитится и не попадает в промпты; задача — `needs_human(secret_file)` со списком файлов: команды прошли бы с файлом в рабочем дереве, а коммит без него мог не собраться |
| Hook'и человека | Изменены `protected.PATHS` (сверка `protected.restore`) или конфиги менеджеров git-hook'ов (`.pre-commit-config.yaml`, `.husky/`, `lefthook.yml`): их код выполнится вне sandbox у человека (раздел 10) | Настройки CLI откатываются, задача — `needs_human`; конфиг git-hook'ов не коммитится, `needs_human` с диффом |
| Значения из `.env*` | Gate-команды читают `.env*`, агент — нет. После команд оркестратор ищет в добавленных строках диффа значения ключей с `KEY`, `TOKEN`, `SECRET`, `PASS`, `PWD`, `CREDENTIAL`, `AUTH`, `DSN`, `PRIVATE` в имени (от 8 символов), в находках для fixer'а заменяет их на `<ключ of файл>`. Значение, которое уже есть в файлах чекпоинта (`git grep -F` по дереву), не секрет: пароль по умолчанию из `.env.example` и его копия в `.env` (решение 2026-10-12, ревью 3а.1) | Значение в диффе — `needs_human(secret_in_diff)` с именами ключей |
| Размер диффа | `git diff --numstat` против чекпоинта | > 1000 — предупреждение в отчёт; > 1500 — `replan` |
| Сообщение коммита | Схема ответа: `type(scope): gist`, ≤ 72 символов, английский; регулярка запрещает `Co-Authored-By`, `Claude`, `Anthropic`, `Generated with` | Перед коммитом: та же сессия продолжается (`--resume`) с правилами и плохим сообщением; её ответ снова проходит gate (сессия могла тронуть файлы); снова плохое — `needs_human(commit_message)` (решение 2026-10-12, раздел 3) |
| Стиль (детерминированная часть шаблона ревью) | Только добавленные строки `.py`, после команд профиля: декоративные разделители в комментариях, markdown (выделение, заголовки) в комментариях и докстрингах, ссылки на `plan.md`, номера задач, шагов и решений (`#12`, `3.5`, `3б`); AST: новое имя уровня модуля, использованное в модуле меньше 3 раз, константы и регулярки тоже (решение 2026-10-12). Не новое — имя, которое было на уровне модуля в одном из изменённых модулей (перенос); не нарушение — имя, на которое ссылаются другие файлы репозитория (`git grep`), dunder-имена, `logger`, `pytestmark`, `pytest_plugins` | Возврат исполнителю (`fixing(style)`); при упавших командах — находки вместе с их выводом |
| Субагенты | `--restricted --tools Bash,Read,Edit,Write`: инструмента `Agent` в сессии нет | — |

Коммит делает оркестратор, автор и подпись — по git config пользователя. Не `git add -A`: в коммит попадают изменённые отслеживаемые файлы и неотслеживаемые, появившиеся за задачу (список неотслеживаемых снимается перед первым шагом), кроме файлов из проверки секретов и файлов, оставленных gate-командами (отчёты, кэши мимо `.gitignore`). Коммит собирается во временном индексе, ветка сдвигается, только если она всё ещё на чекпоинте; реальный индекс потом сбрасывается на коммит, рабочее дерево не трогается.

Откат к чекпоинту тоже точечный: `git reset --hard <checkpoint>` и удаление только тех неотслеживаемых файлов, что появились за шаг. `git clean` по всему каталогу не делаем: там лежат `.env`, сертификаты и прочее окружение.

## 8. Контекст исполнителя (R3)

Промпт задачи собирает оркестратор, агент не читает план и прогресс сам:

- роль: общие правила сессии цикла (`prompts/session.md`) и файл роли (`prompts/implementer.md`, `prompts/fixer.md`) — через `--append-system-prompt-file` вместе с правилами ниже;
- карточка задачи из `plan.json`: цель, критерии приёмки, файлы-подсказки, тесты, которые должны пройти, бюджет диффа;
- решения из плана, помеченные для этой задачи;
- сводка предыдущих задач, собранная кодом: список изменённых файлов и новых публичных символов (`git diff --name-status` + разбор AST). Без неё агент задачи N пишет свою утилиту вместо созданной в задаче N−1;
- правила: `AGENTS.md` agent-loop и `context_file` проекта — через `--append-system-prompt-file`; CLAUDE.md и `.claude/CLAUDE.md` из корня репозитория адаптер добавляет к ним сам (`--restricted` их не читает) вместе с `@path`-импортами — только закоммиченных файлов, глубина 5; CLAUDE.md вложенных каталогов промпт исполнителя велит прочитать самому (selfcheck проверяет передачу);
- язык комментариев и докстрингов из конфига;
- при возобновлении — `handoff.md`.

Ответ исполнителя по схеме: `status` (`done` / `blocked` / `too_big` / `needs_human`), `summary`, `commit_message`, `notes_for_next`, `question`, `split` (предложение разбиения при `too_big`), `operator_actions` (что оператор делает руками после задачи: правки файлов, закрытых для сессии, — `.env*` и другие из `session.md`; цикл пишет их в лог после коммита и списком в конце прогона).

`too_big` — исполнитель сам понял, что задача не влезает в ~1000 строк (правило из `AGENTS.md`), и остановился. Задача уходит в `replan` с его предложением разбиения, не дожидаясь gate по размеру диффа. Лимит размера держат три уровня: планировщик режет задачи, исполнитель останавливается сам, gate (> 1500 строк) ловит то, что прошло мимо обоих. Потолок контекста 150k размер диффа не ограничивает: за одну сессию можно написать несколько тысяч строк, почти ничего не читая.

Агенту разрешено запускать только тесты, относящиеся к задаче (быстрые). Полный прогон делает gate.

| Go-сервисы (gonotifysender*) | — | `test`, `build`, `tidy` | Другой стек |

Вывод: единых целей нет, и менять Makefile рабочих репозиториев ради цикла не стоит. Профиль `loop.toml` лежит вне репозитория (`agent_runs/<repo>/loop.toml` в базе знаний) или в самом репозитории, если так удобнее:

```toml
context_file = "~/andrey_personal_projects/MY-KNOWLEDGE-DATABASE/USEFUL_JOB_NOTES/agent_runs/cms/CLAUDE.md"
doc_lang     = "ru"                             # переопределяет LOOP_DOC_LANG из .env
deps_files   = ["requirements*.txt", "pyproject.toml", "uv.lock"]
secret_patterns = ["*.pem"]

[commands]
install   = "pip install -r requirements.txt"   # шаг оркестратора, с сетью
fmt       = ""                                  # нет форматтера — шаг пропускается
lint      = "flake8"
collect   = "pytest --collect-only -q"          # число тестов; нет — проверка пропускается
test      = "pytest -q -x {changed_tests}"      # быстрый прогон
test_full = "pytest -q ./tests"
up        = "docker compose -p {run_id} up -d --wait"
down      = "docker compose -p {run_id} down -v"
smoke     = "pytest -q tests/smoke"

[timeouts]           # секунды
lint = 120
test_full = 1200

[env]
POSTGRES_PORT = "{free_port}"    # локальный Postgres занимает 5432
```

`{run_id}` и `{free_port}` подставляет оркестратор: параллельные прогоны не делят compose-проект и порты. Подстановка делается один раз при старте прогона, результат лежит в `runs/<run>/profile.json` (шаг 3.2): `up`, сессии, gates и `down` видят одни порты, `loop resume` и доуборка мёртвого прогона берут профиль оттуда. Правка `loop.toml` действует на следующие прогоны. `{changed_tests}` подставляется при каждом запуске gate. Неизвестный ключ, команда или таймаут в профиле — ошибка конфига; команда без таймаута получает 10 минут.

`fmt`, `lint`, `collect`, `test`, `test_full`, `smoke` идут под `sandbox-exec` (раздел 10): окружение — `PATH`, `HOME`, `USER`, `LANG` и `[env]`, свой `TMPDIR` на каждую команду, запись вне репозитория закрыта. Поэтому команды uv пишутся как `uv run --no-sync --no-cache ...` (кэш uv в `$HOME`; синхронизирует `install`), а инструменту с кэшем в `$HOME` кэш задаётся в команде: `BLACK_CACHE_DIR=$TMPDIR black .`. Тесты, которым нужен docker socket (testcontainers), под gate не работают.

`up` выполняется при старте и возобновлении прогона, `down` — при любом выходе из него (в том числе по SIGTERM/SIGHUP) и при доуборке мёртвого прогона (`reap`), если тот оставил сервисы поднятыми: пока они могут быть подняты, лежит метка `runs/<run>/services`. Команды идут в своей группе процессов: по таймауту убивается вся группа.

Глобальный `~/.agent-loop/.env` (шаблон — `.env.example` в репозитории):

```
LOOP_DOC_LANG=ru                 # документация, спецификации, комментарии в коде: ru | en
LOOP_MODEL_PLANNER=opus
LOOP_MODEL_IMPLEMENTER=opus      # и fixer
LOOP_MODEL_CRITIC=opus           # критик плана и ревьюер
```

## 10. Безопасность и настройки сессий

Сейчас: `~/.claude/settings.json` — `defaultMode: bypassPermissions` плюс deny-список (`rm -rf *`, `export *KEY*`, `curl *TOKEN*` и т. п.). Deny-список по шаблонам обходится тривиально: `find -delete`, `python -c "shutil.rmtree(...)"`, `cat .env`, `printenv`. Это защита от случайности, а не от агента, который «решил» что-то сделать.

Для цикла:
- Отдельный `loop-settings.json` (`--restricted --tools Bash,Read,Edit,Write --settings loop-settings.json`: пользовательские и проектные настройки не подтягиваются, шаг 3.1б): allow-список команд (`uv`, `pytest`, `ruff`, `flake8`, `make <цели профиля>`, `git status/diff/log/show`), deny на `git commit/push/reset/checkout/rebase`, `rm -rf`, сетевые утилиты; `sandbox` для Bash (запись только в рабочий каталог и `$TMPDIR`), сеть из sandbox закрыта; `Read`, `Write`/`Edit` разрешены только в рабочем каталоге; чтение `.env*`, `*.pem`, `*.key` и каталогов с учётными данными в `$HOME` (`~/.ssh`, `~/.aws`, `~/.kube`, `~/.docker/config.json` и т. п.) запрещено и инструментам, и Bash в sandbox; `autoMemoryEnabled: false`.
- `.git/` рабочего репозитория: запись в hook'и и конфиг закрыта CLI и sandbox (проверено в этапе 2а), `Edit(.git/**)` в deny.
- Настройки CLI в репозитории (`.claude/settings*.json`, `.claude/rules`, `.claude/hooks`, `.claude/skills`, `.claude/agents`, `.claude/commands`, `.mcp.json`) принадлежат человеку: `Edit` на них в deny, Bash в sandbox их не пишет (шаг 3.0), сессии цикла их не читают (`--restricted`), MCP только из `--mcp-config` (`--strict-mcp-config`). Перед каждой сессией оркестратор сверяет их с копией со старта прогона и откатывает (этап 2b): это защита уже не сессий цикла, а следующей интерактивной сессии человека — hook, подложенный в `.claude/settings.local.json`, выполнился бы у него вне sandbox, а файл обычно в gitignore и в дифф не попадает. Git оркестратора работает вне sandbox, поэтому сам не исполняет код из репозитория: каждый вызов идёт с `-c core.hooksPath=/dev/null -c core.fsmonitor=false`.
- Чистое окружение: `claude` запускается с `env`, где оставлены только `PATH`, `HOME`, `USER`, `LANG`, `TMPDIR` и переменные из профиля репозитория. Без `USER` OAuth-токен не находится в keychain («Not logged in»). Токены и ключи из shell не наследуются.
- Gate-команды исполняют код агента (тесты, `conftest.py`, конфиги линтера), поэтому `fmt`, `lint`, `collect`, `test`, `test_full`, `smoke` идут под `sandbox-exec` (шаг 3.3в, `commands._sandbox`): профиль от `(deny default)` по образцу `@anthropic-ai/sandbox-runtime`; запись — репозиторий и свой временный каталог команды (удаляется после неё), кроме `.git/`, `protected.PATHS`, конфигов git-hook'ов, `.vscode`, `.idea`, `.devcontainer` и `.env*`/`*.pem`/`*.key` (имена без учёта регистра); чтение закрыто для каталогов с учётными данными в `$HOME` (как в `loop-settings.json`, плюс `~/Library/Keychains`) и `*.pem`, `*.key` репозитория, а `.env*` открыт — его значения маскирует gate (раздел 7); сеть — только localhost (тестовые БД из `up`), unix-сокеты закрыты; окружение — `agent.ENV_KEYS` плюс `[env]`. `install`, `up`, `down` идут без обёртки и с полным окружением. `loop selfcheck` проверяет, что sandbox gate пишет в репозиторий и не пишет рядом.
- Инварианты из раздела 7 ловят то, что пропустили настройки.

### Работа в текущей ветке: риски и защиты

| Риск | Защита |
|---|---|
| Незакоммиченные правки человека смешаются с работой агента, попадут в его коммит или пропадут при откате | `loop run` не стартует, если есть изменения в отслеживаемых файлах. Неотслеживаемые файлы на старте запоминаются и не трогаются |
| Человек переключил ветку, сделал коммит или ребейз во время прогона — агент продолжит писать в чужое состояние | Проверка ветки и HEAD перед каждым шагом и перед коммитом (раздел 7) → пауза |
| Агенту видны `.env` и сертификаты (в worktree их бы не было) | Запрет `Read` на эти пути действует и на инструменты, и на Bash в sandbox (S7); токены не наследуются из shell. Остаётся процесс вне sandbox — его агенту не дать (`allowUnsandboxedCommands: false`) |
| `git add -A` закоммитит мусор или секреты | Точечное добавление файлов (раздел 7) |
| Откат к чекпоинту снесёт окружение | Точечный откат, без `git clean` (раздел 7) |
| Два прогона в одном каталоге | Lock-файл `.git/agent-loop.lock` с pid; второй `loop run` отказывается стартовать |
| Служебные файлы цикла (`.loop/handoff.md`) попадут в коммит | `.loop/` добавляется в `.git/info/exclude` при старте |
| Сервис, запущенный человеком с `--reload`, перезапускается на каждой правке агента | Безвредно; если мешает — останавливать сервис на время прогона |
| Агент через Bash подкладывает конфиг менеджера git-hook'ов (`.pre-commit-config.yaml` с `repo: local`, `.husky/*`, `lefthook.yml`) — код выполнится вне sandbox при `git commit` человека (шаг 3.1а) | Коммиты цикла идут с `core.hooksPath=/dev/null` и hook'и не запускают. Gates: изменение этих файлов — `needs_human` с диффом, а не коммит |
| Gate запускает код агента вне sandbox: `pytest` исполняет его `conftest.py` с сетью и `$HOME` | `fmt`/`lint`/`collect`/`test` под `sandbox-exec` (шаг 3.3в). Значения `.env*` gate-командам видны: маскируются в находках и ищутся в диффе, но закодированное значение или значение в игнорируемом файле, который потом прочитает агент, до модели дойти может. Остаток: `install` без обёртки исполняет build-скрипты зависимостей и локальный build-backend из `pyproject.toml`, `up` — `docker-compose.yml`, который агент может править (монтирование `$HOME` в контейнер). Кандидат в gates: изменение `docker-compose*.yml` и `[build-system]` — `needs_human`, как для конфигов git-hook'ов |

Пока прогон идёт, рабочий каталог принадлежит циклу: читать и запускать сервис можно, править файлы и двигать ветку — нет.

Отдельная задача вне цикла: собрать `COLLECTION/claude_settings/` (settings.json + установка) по образцу `claude_statusline`, чтобы глобальные настройки на обеих машинах совпадали.

## 11. Таймауты

| Уровень | Значение по умолчанию | Что ловит |
|---|---|---|
| Команда Bash внутри сессии | `BASH_DEFAULT_TIMEOUT_MS` / `BASH_MAX_TIMEOUT_MS` в окружении цикла (2 / 10 мин) | Зависший тест, запущенный агентом |
| Простой потока | Нет событий `stream-json` дольше максимального таймаута Bash + 2 мин | Зависание самого CLI или сети |
| Шаг целиком | 60 мин | Агент ходит по кругу; мягкая остановка через stop-файл, через 5 мин — жёсткая |
| Gate-команды | Из профиля репозитория | Зависший полный прогон; рекомендуется `pytest-timeout` |

Тесты из цикла не исключаем: агент гоняет только быстрые тесты своей задачи, полный прогон делает gate с собственным таймаутом.

## 12. Все роли на Opus: риски

Главную пользу независимого ревью даёт свежий контекст: критик не видел рассуждений исполнителя и не «помнит», почему решение казалось верным. Это мы получаем и на одной модели. Чего не получаем:

- **Коррелированные слепые зоны.** Одинаково ошибочное представление о поведении библиотеки или API у исполнителя и критика — критик подтвердит ошибку.
- **Предпочтение своего стиля.** Модель мягче оценивает код, написанный в её собственной манере, в том числе признаки AI-кода из шаблона ревью.
- **Принятие рамки плана.** Критик читает план, написанный той же моделью, и склонен спорить с деталями, а не с постановкой.

Что делаем:
- критику — только дифф, карточку задачи и доступ к репозиторию на чтение; без логов исполнителя;
- роль критика — состязательная; каждая блокирующая находка обязана содержать файл:строку и сценарий отказа, без них не блокирует;
- критику — `--effort max`, исполнителю — `high`;
- всё, что можно проверить кодом, уходит из ревью в gates (раздел 7): критику остаётся логика;
- метрика: доля находок критика, которые после правки действительно что-то изменили. Когда появится адаптер Codex, прогоняем обоих критиков на одних и тех же диффах и считаем расхождения. Это ответ на вопрос «насколько хуже» на наших данных, а не на ощущениях.

## 14. Этапы

Каждый этап — серия коммитов ≤ ~1000 строк. Номера коммитов внутри этапа уточняются при старте этапа.

Порядок разработки самого agent-loop:
- Коммитит и пушит только человек, чтобы видеть ход работы. Агент оставляет изменения в рабочем каталоге и предлагает сообщение коммита (английский, `type(module): gist of changes`).
