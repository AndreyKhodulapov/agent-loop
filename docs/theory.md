# Как сделать так, чтобы скорость разработки не убивала качество кода

На человеке: 
- что делать (какую проблему решаем и зачем)
- что считать готовым (критерии, ограничения, компромисы)
- Когда вмешаться (принять, повторить, забрать человеку)
- улучшение продукта (работа над метриками)

За что платят инженеру:
- понять цель
- написать требования
- проверить evidence (доказательство работы и правильности)
- оценка остаточного риска
- принять решение исходя из опыта

На агенте
- сбор контекста
- написание кода
- написание тестов
- прогон проверок
- описание ПР(МР)

Нужно Agentic workflow для написания кода (задача выполняется без участия человека от созвона до ПР) run -> check -> PR

На примере бага

Баг  -> регрессионный тест (сначала)  -> красный до задачи  -> имплементация (пишет агент имплементор) -> e2e тест агентом проверки -> агент критик делает ревью решения (критик работает на другой модели)  ->  все ок -> создание PR

Непонятный сбой  ->  вызов человека.

Yolo mode == dangerously-skip-permissions - агент работает без остановок

ИНВАРИАНТ РАНТАЙМА ОПРЕДЕЛЯЕТ КОД А НЕ МОДЕЛЬ! 

LLM не ждет тесты, CI, получает только результат! LLM не мержит! 

WORKFLOW:
1. SELECT (набор обязательных блоков для каждой задачи)
2. PREPARE (агент делающий план -> plan.md  -> агент критик плана), если принято, то TDD тесты на новое поведение. Если не принято повтор, но не более 2х итераций, чтоб не уйти в цикл. По итогам критик просто оставляет свои заметки в файле с планом
3. IMPLEMENT - реализация кода по плану:
работа агента -> прогон тестов и линтера (без агентв) -> критик (другая модель) -> переход дальше или правки. 
По диффу надо понимать что задето и что должно быть проверено! 
В критик поступает diff и требования, модель другая, если делал Opus, то лучше GPT-5 Codex! Непредвзятость! Контекст не отравлен. 
4. PROVE - поднять сервис в песочнице, дернуть ручку, что была изменена. Скрин если надо, все прикрепляется к ПР. 
5. DELIVER - без агента до прогона и проверки. 

Память вокрфлоу живет вне контекста LLM! postgres-sqlite (разные машины, можно ли решить проблему синхронизации? файлы дешевле?):
задача, план, выбранные блоки, ветка, решения. 

Критик получает только diff и summary задачи, дает вердикт

Верификация и пруфы без LLM! - все проверки и пруфы, а результат по идее можно отдать в модель. 

Метрики оценки - логгирование действий (вплоть до подключения Prometheus и Graphana):
 - Success rate - сколько задач дошли до нужного terminal state без человека (цель более 80%) = завершено без человека / всего запусков
 - Needs human - как часто воркфлоу вызывает человека (цель менее 15%) - причины CI, неясная задача, исчерпан цикл, инфра. 
 - Attemps - сколько итераций нужно до принятия (implement - verify - critic растет - дело в промпте!)
 - Стоимость - во сколько обходится готовая задача и сколько она занимает. От приема в работу до ПР. 

Не экономить на критике! Дорогая умная модель.
